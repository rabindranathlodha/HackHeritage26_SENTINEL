What it costs to run SENTINEL

Every figure below was measured on the working system against 3,000 synthetic personnel — not estimated. Where a number rests on an assumption, the assumption is named.

Q1

Who pays, and for what?

This is not a subscription product. Personnel welfare data cannot leave government infrastructure, so SENTINEL is built to be deployed and owned by the force, not rented from a vendor. That decision shapes the whole cost structure.

The realistic funding route is the existing Modernisation of Police Forces umbrella or the CAPF welfare allocation, procured through GeM, with an annual maintenance contract covering retraining, corpus updates and support. Capital cost is a one-time server; the recurring cost is almost entirely people.

Runtime dependencies
None external

Every model runs locally — gradient-boosted trees, the multilingual encoder, the embedding model and the vector store. The system can run air-gapped.

Data egress
Zero by design

No welfare record leaves the deployment. The optional policy-recommendation path defaults to quoting retrieved text rather than calling a hosted model.

Vendor lock-in
Open components

PostgreSQL, XGBoost, an AI4Bharat encoder, ONNX. No proprietary runtime to renew, and the trained artifacts are files the force holds.

Q2

Will it scale to a force of this size?

Comfortably, and the reason is that the expensive model only runs when someone actually writes something. Behavioural scoring — the part that runs for everybody, every cycle — costs 8.5 milliseconds per person end to end.

Measured on one CPU thread pool, per person
Stage Latency Runs for
Feature engineering from 180-day history 0.6 ms Everyone, every cycle
Model A — behavioural risk, with SHAP 7.9 ms Everyone, every cycle
Fusion, banding, escalation decision 0.008 ms Everyone, every cycle
Model C — physiological deviation 12.0 ms Consenting personnel only
Model B — self-report text, CPU 212.2 ms Only when text is submitted

At 8.5 ms per person, scoring 1,000 personnel takes 8.5 seconds on a single thread. A force of 325,000 (sanctioned strength — verify against current establishment) scores in about 46 minutes single-threaded, or roughly six minutes on eight cores. That is a nightly batch job on one mid-range server, not a cluster.

Storage is similarly undramatic. A daily HR-signal row is 304 bytes, so a year of behavioural history costs 111 KB per person — about 36 GB a year for 325,000 people, before compression. Score history at weekly cadence adds roughly 11 GB a year.

Model B is the one costly component, and it is event-driven: it runs when a person chooses to write something, not on a schedule. If one person in ten submits a self-report each week, that is under two hours of single-threaded compute per week across the entire force.

Q3

How many alerts will my welfare officers actually get?

This is the question that decides whether the system gets used or ignored, so it is the one we measured most carefully. Alert volume is a dial, not a consequence — and the dial has a published curve.

A single parameter (τ) sets how confident the model must be before it places someone in the top band and raises a pending review. Moving it trades officer workload against how many genuinely high-risk people are surfaced. Both sides of that trade were measured out-of-fold across 3,000 people.

Read it as a staffing decision. Roughly tripling alert volume — 12.7 to 41.0 per thousand — roughly doubles how much of the highest-risk group reaches a human. An officer responsible for 500 personnel sees about 16 pending reviews per full scoring cycle at the setting now in force.

The database enforces one open alert per person, so a repeatedly-flagged individual does not generate a queue. Steady-state volume is therefore governed by how quickly officers close reviews, not by scoring frequency.

Q4

How does it get adopted?

Not force-wide on day one. The behavioural model needs 90 days of history before its windows are meaningful, and welfare officers need to trust the queue before they will work it.

Phase 1

One battalion, shadow mode

Scores computed and logged, no alerts raised. Establishes the 90-day history and lets officers compare what the system surfaces against what they already know. τ is calibrated here against real caseload capacity.

Phase 2

Alerts live, behavioural signal only

Pending reviews reach assigned welfare officers. Self-report and wearable consent stay closed. This is the phase that tests whether the queue is workable before any additional data is asked for.

Phase 3

Self-report and consented biometrics

The two optional signals open, each individually consented. The system already functions fully without either — that is a design constraint, not a fallback — so uptake can be slow without degrading service.

Phase 4

Sector rollout, annual re-audit

Extension by sector, with the bias audit re-run on live cohorts each year. Recall drift and any cohort whose interval separates from the overall rate become contract deliverables, not discretionary checks.

Q5

What does year two cost?

Compute and storage are close to a rounding error at this scale. The recurring cost is human, and it falls into three lines.

Recurring cost drivers, in order of size
LineDriverCadence
Welfare officer time Set by τ — see the capacity curve above Continuous
Model retraining and bias re-audit Distribution drift as postings and rotations change Annual
Policy corpus maintenance New welfare circulars superseding old guidance As issued
Infrastructure One server class; ~50 GB/year growth Refresh cycle

Retraining is cheap in compute — the behavioural model trains in under two minutes on 3,000 people — and expensive in review: the bias audit and its confidence intervals have to be read by someone before a new model is promoted.

Q6

What will you not claim?

A business case for a welfare system invites a return-on-investment figure built on incidents prevented. We will not offer one, and the reason matters more than the omission.

Claims deliberately withheld

  • No incidents-prevented figure. You cannot count what did not happen, and attributing an absence to this system would be unfalsifiable. Any ROI built on that number is arithmetic on a guess.
  • No clinical outcome claim. The system surfaces elevated welfare-risk indicators for human review. It does not diagnose, detect a condition, or predict an act — a boundary enforced in code on every response, not just in copy.
  • Detection is 64.4%, not "high accuracy". At the setting in force, roughly a third of the highest-risk group is still missed by the behavioural signal alone. Self-report override and sustained-trend escalation exist to catch some of that; neither closes the gap entirely.
  • Costs are measured on synthetic data. 3,000 generated personnel with calibrated but unverified ranges. Latency and storage figures transfer; alert volumes depend on real prevalence, which nobody here has measured.

What the system does offer is a workload curve an operations owner can plan against, an audit that reports its own uncertainty, and a deployment that keeps welfare data inside the force. Those are defensible. A prevented-suicide count is not.
